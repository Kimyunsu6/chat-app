## 3. 큰 그림 — 식당에 비유하면

| 프로그램 부분 | 식당 비유 | 이 프로젝트에서 |
|------|------|------|
| **프론트엔드** | 손님이 보는 홀, 메뉴판 | `public/index.html` (화면 + 버튼 동작) |
| **백엔드 (서버)** | 주방. 주문을 받아 처리 | `src/index.js` 의 Worker |
| **Durable Object** | 테이블마다 붙어 있는 전담 직원 | `ChatRoom` (채팅방 하나당 하나) |
| **DB (D1)** | 창고 겸 장부 | `chat-app-db` (회원·친구·방 정보) |

```
 [브라우저 = 프론트엔드]
   │  ① 일반 요청 (fetch)  : 로그인, 친구 목록, 방 만들기 ...
   │  ② WebSocket (/ws)   : 실시간 채팅
   ▼
 [Worker = 백엔드 입구]  ── 로그인 확인, 권한 확인
   │                  │
   │                  └──▶ [D1 DB] 회원 / 로그인 / 친구 / 방 / 방 멤버
   ▼
 [ChatRoom Durable Object]  ── 방 번호마다 1개
   └──▶ [방 전용 SQLite] 그 방의 메시지
```

## 5. 프론트엔드 (`public/index.html`)

**프론트엔드 = 사용자가 브라우저에서 보고 누르는 부분.**

### 화면 3개

| 화면 | 언제 보이나 | 내용 |
|------|------|------|
| 로그인 화면 | 로그인 안 했을 때 | 아이디·비밀번호 입력, 로그인 / 회원가입 버튼 |
| 목록 화면 (`/`) | 로그인했을 때 | 내 채팅방 목록, 친구 추가, 받은 신청, 친구 목록, 단톡방 만들기 |
| 채팅 화면 (`/chat/번호`) | 방을 눌렀을 때 | 메시지 목록, 입력칸 |

### 서버와 이야기하는 2가지 방법

| 방법 | 비유 | 쓰는 곳 |
|------|------|------|
| `fetch` (HTTP 요청) | 편지 한 통 보내고 답장 받기. 한 번 하고 끝 | 로그인, 친구 신청, 방 목록 불러오기 등 |
| `WebSocket` | 전화 연결. 끊기 전까지 계속 주고받음 | 채팅 메시지 (실시간) |

> 채팅에 WebSocket을 쓰는 이유: `fetch`는 내가 물어봐야만 답이 오지만, WebSocket은 **다른 사람이 보낸 메시지를 서버가 먼저 나에게 보내 줄 수 있다.**

## 6. 백엔드 — Worker (`src/index.js` 아래쪽)

**Worker = Cloudflare 서버에서 돌아가는 코드.** 모든 요청이 처음 도착하는 "입구"이다.
주소(`/api/...`)를 보고 어떤 함수로 보낼지 정한다.

### API 목록

| 주소 | 방식 | 하는 일 |
|------|------|------|
| `/api/signup` | POST | 회원가입 (가입하면 바로 로그인됨) |
| `/api/login` | POST | 로그인 |
| `/api/logout` | POST | 로그아웃 |
| `/api/me` | GET | 지금 로그인한 사람이 누구인지 |
| `/api/friends/request` | POST | 아이디로 친구 신청 |
| `/api/friends/accept` | POST | 받은 신청 수락 |
| `/api/friends` | GET | 내 친구 목록 |
| `/api/friends/requests` | GET | 내가 받은 신청 목록 |
| `/api/dm` | POST | 친구와 1:1 방 열기 (없으면 만들기) |
| `/api/groups` | POST | 단톡방 만들기 (친구 2~20명) |
| `/api/conversations` | GET | 내 방 목록 (최근 메시지 온 순서) |
| `/api/conversation` | GET | 방 하나의 제목 |
| `/ws` | WebSocket | 채팅방 접속 |

> **GET** = 조회만 할 때, **POST** = 무언가를 바꿀 때.

## 7. 백엔드 — Durable Object (`ChatRoom`)

**Durable Object = 이름마다 딱 하나만 존재하는 작은 서버 + 전용 저장 공간.**

| 질문 | 답 |
|------|------|
| 몇 개 있나? | 방 번호마다 1개 (`"conversation:12"` 같은 이름) |
| 무슨 일을 하나? | 그 방에 접속한 사람들의 WebSocket 연결을 들고 있다가, 메시지가 오면 **모두에게 나눠 준다** |
| 메시지는 어디 저장? | Durable Object마다 있는 **자기 전용 SQLite** 의 `messages` 표 |
| 들어오면 뭐가 보이나? | 최근 메시지 50개를 먼저 보내 준다 |
| 왜 썼나? | 같은 방 사람들이 반드시 **같은 곳**에 연결되어야 메시지를 나눠 줄 수 있기 때문. 일반 Worker는 요청마다 다른 곳에서 실행될 수 있다 |

## 8. 데이터베이스 (DB)

이 앱은 저장 공간을 **2군데** 쓴다.

| 저장 공간 | 저장하는 것 | 이유 |
|------|------|------|
| **D1** (`chat-app-db`) | 회원, 로그인, 친구, 방, 방 멤버 | 모든 방이 함께 봐야 하는 정보. SQL 표라서 찾기·중복 막기가 쉬움 |
| **Durable Object 안 SQLite** | 각 방의 메시지 | 방마다 따로 저장하면 한 곳에 몰리지 않음 |

### D1 표 5개 (`schema.sql`)

| 표 | 저장하는 것 | 중요한 칸 |
|------|------|------|
| `users` | 회원 | `username`(중복 불가), `password_hash`, `salt` |
| `sessions` | 로그인 상태 | `token`(쿠키 값), `user_id`, `expires_at`(7일 뒤 만료) |
| `friends` | 친구 신청·관계 | `status` = `pending`(대기) / `accepted`(친구), `pair_key` |
| `conversations` | 대화방 | `type` = `dm`(1:1) / `group`(단톡), `last_message_at` |
| `conversation_members` | 어느 방에 누가 있는지 | `conversation_id` + `user_id` |

### 표끼리의 관계

```
users ─┬─ sessions            (한 사람이 여러 기기에서 로그인 가능)
       ├─ friends              (두 사람 사이에 1줄)
       └─ conversation_members ── conversations
                                   └─ (방 번호로) ChatRoom 의 messages
```

### 알아 두면 좋은 아이디어

| 아이디어 | 설명 |
|------|------|
| `pair_key` | 3번과 7번이면 누가 신청하든 `"3:7"`. UNIQUE라서 두 사람 사이에 신청이 두 개 생길 수 없음 |
| `dm_key` | 같은 원리. 같은 두 사람의 1:1 방은 딱 하나만 생김 |
| `last_message_at` | 메시지가 오면 시간을 갱신 → 방 목록에서 맨 위로 |
| `?` 자리 채우기 | SQL에 값을 직접 붙이지 않고 `?`로 넣어서 **SQL 인젝션** 공격을 막음 |

## 9. 흐름 따라가 보기

### (1) 로그인

| 순서 | 어디서 | 하는 일 |
|------|------|------|
| 1 | 브라우저 | 아이디·비밀번호를 `/api/login`으로 보냄 |
| 2 | Worker | D1 `users`에서 아이디 찾기 → 비밀번호를 같은 방법으로 해시해서 비교 |
| 3 | Worker | 맞으면 랜덤 토큰을 만들어 `sessions`에 저장 |
| 4 | Worker | 토큰을 **쿠키**로 브라우저에 줌 |
| 5 | 브라우저 | 다음 요청부터 쿠키가 자동으로 붙음 → 서버가 "누구인지" 앎 |

### (2) 메시지 보내기

| 순서 | 어디서 | 하는 일 |
|------|------|------|
| 1 | 브라우저 | `/ws?conversation=12` 로 WebSocket 연결 요청 |
| 2 | Worker | 로그인했나? 이 방 멤버인가? 확인 (아니면 거절) |
| 3 | Worker | `conversation:12` Durable Object에 연결을 넘김 (**서버가 확인한 아이디**도 같이) |
| 4 | ChatRoom | 최근 메시지 50개를 보내 줌 |
| 5 | 브라우저 | 메시지 입력 → WebSocket으로 보냄 |
| 6 | ChatRoom | 메시지 저장 → 접속 중인 모두에게 보냄 → D1의 `last_message_at` 갱신 |

## 10. 보안 — 질문 받기 쉬운 부분

| 위험 | 막은 방법 |
|------|------|
| DB가 털리면 비밀번호 노출 | 비밀번호 원문은 저장 안 함. **PBKDF2-SHA256 10만 번 + 사람마다 다른 salt** 로 해시만 저장 |
| 해시 비교 시간으로 추측 | `timingSafeEqual`로 비교 (항상 같은 시간이 걸림) |
| 어떤 아이디가 있는지 알아내기 | 아이디 없음 / 비번 틀림 → **같은 오류 메시지** |
| 자바스크립트로 쿠키 훔치기 | 쿠키에 `HttpOnly` |
| 다른 사이트에서 몰래 요청 | 쿠키에 `SameSite=Lax`, WebSocket은 `Origin` 확인 |
| 남의 이름으로 메시지 보내기 | 이름은 브라우저가 아니라 **서버가 쿠키로 확인한 아이디**를 붙임 |
| 남의 방 엿보기 | 방 정보·접속 모두 **멤버인지 확인**. 멤버 아니면 "없는 방"과 같은 답 |
| SQL 인젝션 | 모든 SQL에 `?` 자리 채우기 사용 |
| 친구 아닌 사람과 대화 | 1:1·단톡은 **친구만** 고를 수 있음 |

## 11. 기술을 고른 이유

| 고른 것 | 대신 생각한 것 | 고른 이유 |
|------|------|------|
| 회원 정보 → **D1** | Durable Object 1개 | 전체가 쓰는 DO 1개는 병목이 됨 (공식 문서에서 하지 말라고 함) |
| 회원 정보 → **D1** | KV | KV는 저장이 퍼지는 데 시간이 걸려서 같은 아이디 동시 가입을 막기 어려움 |
| 채팅 → **WebSocket** | fetch로 계속 물어보기 | 실시간으로 바로 받을 수 있고, 쓸데없는 요청이 없음 |
| 채팅방 → **Durable Object** | Worker만 쓰기 | 같은 방 사람을 한곳에 모아야 메시지를 나눠 줄 수 있음 |

## 13. 코드를 고치는 과정 (AI 없이 사람이 할 때)

### 전체 순서 한눈에 보기

```
① 새 브랜치 만들기  →  ② VS Code로 코드 수정  →  ③ (DB를 바꿨다면) 표 반영
      →  ④ 로컬 서버 켜기  →  ⑤ Postman·브라우저로 테스트  →  ⑥ DB 값 확인
      →  ⑦ 커밋·푸시  →  ⑧ GitHub에서 PR·머지  →  ⑨ master 최신으로 받기  →  (⑩ 배포)
```

| 순서 | 할 일 | 쓰는 도구 | 왜 하나 |
|------|------|------|------|
| ① | 새 브랜치 만들기 | 터미널 (git) | master(완성본)를 건드리지 않고 따로 작업하려고 |
| ② | 코드 수정 | VS Code | 기능 추가·버그 수정 |
| ③ | DB 표 반영 | 터미널 (wrangler) | `schema.sql`만 고치면 DB는 그대로라서, 직접 실행해 줘야 함 |
| ④ | 로컬 서버 켜기 | 터미널 (wrangler) | 내 컴퓨터에서 Cloudflare를 흉내 내서 실행 |
| ⑤ | 테스트 | Postman, 브라우저 | 백엔드 API는 Postman으로, 화면은 브라우저로 확인 |
| ⑥ | DB 값 확인 | 터미널 (wrangler) | 데이터가 제대로 저장됐는지 눈으로 확인 |
| ⑦ | 커밋·푸시 | 터미널 (git) | 변경 내용을 기록하고 GitHub에 올림 |
| ⑧ | PR·머지 | GitHub 웹사이트 | 변경 내용을 한 번 더 보고 master에 합침 |
| ⑨ | 최신 받기 | 터미널 (git) | 내 컴퓨터의 master도 GitHub와 똑같이 맞춤 |
| ⑩ | 배포 | 터미널 (wrangler) | 실제 인터넷 주소에 올림 (**이 프로젝트는 아직 안 함**) |

### ① 새 브랜치 만들기

```powershell
cd C:\Users\yunsu\Desktop\projects\chatting\chat-app
```

| 명령어 | 뜻 |
|------|------|

| `git pull` | GitHub에 있는 최신 내용을 내 컴퓨터로 받기 |

> 브랜치 = "복사본 작업 공간". 망가뜨려도 master는 안전하다.

### ② VS Code로 코드 수정 — 무엇을 고치느냐에 따라 파일이 다름

| 바꾸고 싶은 것 | 고칠 파일 | 예시 |
|------|------|------|
| 화면 (프론트엔드) | `public/index.html` | 버튼 추가, 글자 색 바꾸기 |
| 서버 기능 (백엔드) | `src/index.js` | 새 API 만들기 (`/api/friends/reject` 등) |
| 채팅방 동작 | `src/index.js` 의 `ChatRoom` | 메시지 저장 방식 바꾸기 |
| DB 표 | `schema.sql` | 새 표나 새 칸 추가 |
| Cloudflare 설정 | `wrangler.jsonc` | 새 DB·Durable Object 연결 |

보통 기능 하나를 만들면 **3개를 같이** 고친다.

| 순서 | 예: "친구 신청 거절" 기능 |
|------|------|
| 1. DB | (필요하면) `schema.sql`에 칸 추가 |
| 2. 백엔드 | `src/index.js`에 `rejectFriend` 함수 + `/api/friends/reject` 주소 추가 |
| 3. 프론트엔드 | `index.html`에 "거절" 버튼 + 버튼을 누르면 `fetch("/api/friends/reject")` |

> 순서는 **DB → 백엔드 → 프론트**가 편하다. 아래쪽(저장)부터 만들어야 위쪽(화면)에서 쓸 수 있으니까.

### ⑤-1 Postman으로 백엔드(API) 테스트

**Postman = 화면 없이 서버에 직접 요청을 보내 보는 프로그램.**
프론트엔드를 아직 안 만들었어도 백엔드가 맞게 동작하는지 확인할 수 있다.

#### 기본 사용법

| 칸 | 넣을 것 | 예: 로그인 |
|------|------|------|
| 방식 | GET / POST | `POST` |
| 주소 | 서버 주소 + API | `http://127.0.0.1:8787/api/login` |
| Body | `raw` → `JSON` 선택 후 입력 | `{ "username": "alice", "password": "password123" }` |
| Send | 누르면 요청 보냄 | |
| 결과 | 아래에 상태 코드 + 답 | `200` / `{ "username": "alice" }` |

#### 이 프로젝트에서 테스트하는 순서

| 순서 | 방식 | 주소 | Body | 기대 결과 |
|------|------|------|------|------|
| 1 | POST | `/api/signup` | `{ "username": "alice", "password": "password123" }` | 200, 쿠키 생김 |
| 2 | GET | `/api/me` | 없음 | 200, `alice` |
| 3 | POST | `/api/friends/request` | `{ "username": "bob" }` | 200 (bob이 먼저 가입돼 있어야 함) |
| 4 | GET | `/api/friends/requests` | 없음 | (bob으로 로그인해서) 받은 신청 보임 |
| 5 | POST | `/api/friends/accept` | `{ "id": 1 }` | 200 |
| 6 | POST | `/api/dm` | `{ "username": "bob" }` | 200, `{ "id": 방번호 }` |
| 7 | POST | `/api/logout` | 없음 | 200 |
| 8 | GET | `/api/me` | 없음 | **401** (로그아웃됐으니까) |

#### 꼭 알아야 할 점

| 내용 | 설명 |
|------|------|
| 쿠키 | 로그인하면 Postman이 쿠키를 자동 저장해서 다음 요청에 붙여 준다. (주소창 아래 **Cookies** 에서 확인) |
| 두 사람 테스트 | 쿠키가 하나라서 alice → 로그아웃 → bob 로그인 처럼 번갈아 해야 한다 |
| 실패도 테스트 | 틀린 비밀번호(401), 없는 아이디(404), 로그인 안 함(401) 처럼 **거절돼야 하는 경우**도 꼭 확인 |
| WebSocket | Postman에서 New → **WebSocket** 으로 `ws://127.0.0.1:8787/ws?conversation=1` 접속 가능. 쿠키가 안 붙으면 Headers에 `Cookie` = `session=토큰값` 직접 입력 |

#### 상태 코드 읽는 법

| 코드 | 뜻 | 이 프로젝트에서 |
|------|------|------|
| 200 | 성공 | 정상 처리 |
| 101 | 연결 바꿈 성공 | WebSocket 연결됨 |
| 400 | 요청이 잘못됨 | 비밀번호 너무 짧음, 값 빠짐 |
| 401 | 로그인 필요 / 로그인 실패 | 쿠키 없음, 비밀번호 틀림 |
| 403 | 권한 없음 | 친구 아님, 방 멤버 아님 |
| 404 | 없음 | 없는 아이디, 없는 방 |
| 409 | 충돌 | 이미 있는 아이디, 이미 친구 |
| 500 | 서버 오류 | 코드 버그 → `wrangler dev` 터미널에서 오류 확인 |

> Postman 대신 PowerShell에서 `curl.exe`로도 할 수 있다.
> `curl.exe -X POST http://127.0.0.1:8787/api/login -H "Content-Type: application/json" -d '{\"username\":\"alice\",\"password\":\"password123\"}' -c cookie.txt`

### ⑤-2 브라우저로 화면(프론트엔드) 테스트

| 할 일 | 방법 |
|------|------|
| 접속 | `http://127.0.0.1:8787` |
| 여러 사람 | 크롬 일반 + 크롬 시크릿 + 엣지 (쿠키가 브라우저마다 따로) |
| 오류 보기 | `F12` → **Console** 탭 (빨간 글자가 오류) |
| 요청 보기 | `F12` → **Network** 탭 → 버튼을 누를 때 어떤 API가 무슨 코드로 왔는지 보임 |
| 쿠키 보기 | `F12` → **Application** → Cookies |
| 고쳤는데 안 바뀜 | `Ctrl + Shift + R` (강력 새로고침) |

> Network 탭은 "브라우저 안의 Postman"이다. 화면에서 문제가 생기면 여기서 **프론트 문제인지 백엔드 문제인지** 가린다.
> 요청이 200인데 화면이 이상함 → 프론트 문제 / 요청이 400·500 → 백엔드 문제

## 14. 예상 질문과 답

| 질문 | 짧은 답 |
|------|------|
| 프론트엔드와 백엔드는 뭐가 달라요? | 프론트는 브라우저에서 보이는 화면(`index.html`), 백엔드는 Cloudflare 서버에서 돌아가며 로그인 확인·저장을 하는 코드(`src/index.js`) |
| 서버는 어디에 있어요? | 내 컴퓨터가 아니라 **Cloudflare**의 서버. 지금은 개발용으로 내 컴퓨터에서 흉내 내는 중(`wrangler dev`) |
| 실시간은 어떻게 돼요? | WebSocket으로 연결을 계속 열어 두고, 채팅방 Durable Object가 메시지를 모두에게 보냄 |
| Durable Object가 뭐예요? | 이름마다 하나만 있는 작은 서버 + 저장 공간. 이 앱에선 채팅방 하나 = Durable Object 하나 |
| DB는 뭘 써요? | 회원·친구·방 정보는 D1(SQL DB), 메시지는 각 방 Durable Object 안의 SQLite |
| 왜 메시지는 D1에 안 넣었어요? | 방마다 따로 저장하면 한 DB에 부담이 몰리지 않고, 메시지를 받는 곳(채팅방)에서 바로 저장할 수 있어서 |
| 비밀번호는 어떻게 저장해요? | 원문은 저장 안 하고, salt를 섞어 10만 번 해시한 값만 저장 |
| 로그인 유지는 어떻게 해요? | 로그인하면 랜덤 토큰을 DB와 쿠키에 같이 저장. 요청마다 쿠키의 토큰을 DB에서 찾아 누구인지 확인. 7일 뒤 만료 |
| 남의 대화를 볼 수 있나요? | 아니요. 서버가 매번 "이 방 멤버인가"를 DB에서 확인 |
| 같은 친구와 1:1 방이 여러 개 생기지 않나요? | `dm_key`("3:7")가 UNIQUE라서 하나만 생김 |
| 테스트는 어떻게 했어요? | 서버 검사 스크립트(32개 통과) + 브라우저 3개(크롬·시크릿·엣지)로 alice·bob·carol 직접 확인 |
| 왜 브라우저를 3개 썼어요? | 로그인 쿠키는 브라우저마다 따로라서, 여러 사람을 동시에 흉내 내려면 창을 따로 열어야 함 |
| 왜 아직 배포 안 했어요? | 로그인 시도 횟수 제한이 없어 공개하면 비밀번호 맞히기 공격·스팸 가입이 가능해서 |
| 어려웠던 점은? | 검사 스크립트가 오류를 실패로 안 세서 "통과"로 잘못 나왔던 것, 단톡방 만들다 실패하면 빈 방이 남던 버그 |
| 다음엔 뭘 해요? | 5단계: 안 읽은 메시지 수, 접속 중 표시. 6단계: `@AI`로 부르면 답하는 AI |
| 코드를 고치면 어떤 순서로 확인해요? | 브랜치 → VS Code 수정 → (DB면 표 반영) → `wrangler dev` → Postman으로 API, 브라우저로 화면 → DB 값 확인 → 커밋·푸시 → PR·머지 |
| Postman은 왜 써요? | 화면 없이 백엔드 API만 따로 확인할 수 있어서. 문제가 프론트인지 백엔드인지 나눠 볼 수 있음 |

## 15. 용어 사전

| 용어 | 뜻 |
|------|------|
| 프론트엔드 | 사용자가 보는 화면 쪽 |
| 백엔드 | 서버에서 돌아가는 쪽 |
| API | 프론트가 백엔드에 "이거 해 줘" 하고 부르는 주소 |
| Worker | Cloudflare에서 돌아가는 백엔드 코드 |
| Durable Object | 이름마다 하나뿐인 작은 서버 + 저장 공간 |
| D1 | Cloudflare의 SQL 데이터베이스 |
| SQL | DB 표에 저장·조회하는 언어 (`SELECT`, `INSERT` ...) |
| 표(테이블) | 엑셀 시트처럼 칸과 줄로 된 저장 형태 |
| WebSocket | 끊기 전까지 계속 주고받는 연결 |
| 쿠키 | 브라우저가 저장했다가 요청마다 자동으로 붙여 보내는 작은 값 |
| 세션 / 토큰 | "이 사람은 로그인했다"를 나타내는 랜덤 글자 |
| 해시 | 원래 값으로 되돌릴 수 없게 바꾼 글자 |
| salt | 해시하기 전에 섞는 사람마다 다른 랜덤 값 |
| UNIQUE | 표에서 같은 값이 두 번 들어갈 수 없다는 규칙 |
| `wrangler` | Cloudflare 개발 도구 (`npx wrangler dev`로 서버 켜기) |
| PR | GitHub에서 "내 변경을 master에 합쳐 주세요" 하는 요청 |
| 브랜치 | master를 건드리지 않고 따로 작업하는 복사본 공간 |
| 커밋 | 바뀐 내용을 메시지와 함께 내 컴퓨터에 기록하는 것 |
| 푸시 / 풀 | 푸시 = GitHub에 올리기, 풀 = GitHub에서 받아오기 |
| 머지 | 브랜치의 변경을 master에 합치는 것 |
| 배포 | 실제 인터넷 주소에 올려서 누구나 쓰게 하는 것 |
| Postman | 화면 없이 서버 API에 직접 요청을 보내 보는 프로그램 |
| 상태 코드 | 서버 답의 결과 번호 (200 성공, 401 로그인 필요, 500 서버 오류 ...) |
| 로컬 | 내 컴퓨터 (`--local`) ↔ 리모트 = Cloudflare 실제 서버 (`--remote`) |
| F12 개발자 도구 | 브라우저에서 오류(Console)·요청(Network)·쿠키(Application)를 보는 창 |
